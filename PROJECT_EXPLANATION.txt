SECTION 1: WHAT IS THIS PROJECT?
------------------------------------------------------------------------

This is a production-grade, AI-powered CCTV Surveillance System that:

  - Connects to multiple IP/RTSP cameras simultaneously (like security
    cameras in malls, offices, banks, airports)
  - Automatically detects every human face in the video feed
  - Recognizes whether the person is KNOWN (registered in database)
    or UNKNOWN (a stranger)
  - Tracks each person across video frames so they are counted only ONCE
    (no duplicate records)
  - Saves photos and information of unknown persons
  - Shows everything on a live real-time web dashboard
  - Provides a professional REST API for integration with other systems

Real-world use cases:
  → Office/factory attendance and access control
  → Shopping mall customer behavior analysis
  → Bank branch security monitoring
  → Airport / border surveillance
  → School / college campus safety

3.1  YOLOv8  (You Only Look Once v8)
══════════════════════════════════════

WHAT IT IS:
  YOLOv8 is a state-of-the-art deep learning model made by Ultralytics.
  "YOLO" means it scans the entire image in ONE PASS (unlike older methods
  that scanned multiple times). Version 8 is the latest and fastest.

WHAT IT DOES IN OUR PROJECT:
  - Takes each video frame from the camera
  - Scans it and finds ALL faces in that frame
  - Returns bounding boxes: [x1, y1, x2, y2] — coordinates of each face
  - Returns confidence score: how sure it is (0.0 to 1.0)
  - We only accept faces with confidence > 0.5 (50%)

WHY WE CHOSE IT:
  - Extremely FAST — can process 30+ frames per second on GPU
  - Very ACCURATE — 96%+ detection rate even on small/blurry faces
  - Handles multiple faces in one frame simultaneously
  - Works even in poor lighting conditions

HOW IT WORKS (SIMPLE EXPLANATION):
  Imagine dividing the photo into a grid of squares.
  Each grid cell "votes" on whether it contains a face and where exactly.
  All votes are combined and the best detections are selected.
  This happens in 30-50 milliseconds — faster than a blink!

FALLBACK:
  If YOLOv8 is not available, we fall back to OpenCV's Haar Cascade
  which is an older but reliable face detector built into OpenCV.

FILES USED: backend/face_detection.py


══════════════════════════════════════════
3.2  InsightFace  (Face Recognition AI)
══════════════════════════════════════════

WHAT IT IS:
  InsightFace is a powerful open-source face recognition library.
  It was developed by researchers and is used by many production systems.
  It converts a face image into a "mathematical signature" called an
  EMBEDDING — a list of 512 numbers that uniquely represent that face.

WHAT IT DOES IN OUR PROJECT:
  Step 1: Takes the cropped face image (detected by YOLO)
  Step 2: Generates a 512-dimensional embedding vector
           Example: [0.23, -0.45, 0.87, 0.12, ... ] (512 numbers)
  Step 3: Compares this with all KNOWN faces in our database
  Step 4: If similarity >= 0.75 → "KNOWN person, name = John Doe"
           If similarity < 0.75  → "UNKNOWN person"

WHAT IS AN EMBEDDING?
  Think of it like a fingerprint, but for faces.
  Every person has a unique set of 512 numbers.
  Even different photos of the same person will give very similar numbers.
  Photos of different people give very different numbers.

WHAT IS COSINE SIMILARITY?
  This is how we compare two embeddings.
  - Score = 1.0 → Exact same person (identical)
  - Score = 0.9+ → Almost certainly same person
  - Score = 0.75 → Our threshold — we say "same person"
  - Score = 0.5 → Probably different person
  - Score = 0.0 → Completely different

  Formula: similarity = (A · B) / (|A| × |B|)
  Where A and B are the two 512-dimension vectors.

WHY WE CHOSE IT:
  - 99%+ accuracy on LFW (standard face recognition benchmark)
  - Fast — < 10ms per face
  - Handles glasses, hats, partial occlusion, different angles

FILES USED: backend/face_recognition.py

3.3  DeepSORT  (Person Tracking)
══════════════════════════════════════

WHAT IT IS:
  DeepSORT (Deep Simple Online and Realtime Tracking) is a tracking
  algorithm that assigns a consistent ID to each person across multiple
  video frames. It combines two techniques:
    1. Kalman Filter — predicts WHERE the person will be next frame
    2. Hungarian Algorithm — matches predictions to actual detections

THE PROBLEM IT SOLVES:
  Without tracking:
    Frame 1: Detect unknown person → Save to database (entry #1)
    Frame 2: Same person → Save again (entry #2) — DUPLICATE!
    Frame 30: Same person → 30 entries for one person — USELESS!

  With DeepSORT:
    Frame 1: Detect unknown person → Assign Track ID = 5 → Save once
    Frame 2: Same person → Recognize Track ID = 5 → Just update timestamp
    Frame 30: Same person → Still Track ID = 5 → Still just one record

  Result: ONE clean database entry per unique person!

HOW KALMAN FILTER WORKS (SIMPLE):
  Imagine you see a person walking left-to-right.
  The Kalman Filter says: "Based on their speed and direction,
  next frame they should be about 10 pixels to the right."
  When we detect them next frame, we match them to that prediction.
  This works even if they're briefly blocked (occluded).

HOW HUNGARIAN ALGORITHM WORKS:
  If we have 3 detections and 4 existing tracks,
  we need to figure out which detection = which track.
  The Hungarian Algorithm finds the OPTIMAL assignment
  to minimize total matching cost.

  Like solving: "Which taxi should pick up which passenger
  to minimize total driving distance for everyone?"

DEEPSORT PARAMETERS WE CONFIGURED:
  - max_age = 30       → Keep track alive for 30 frames after last seen
  - min_hits = 3       → Need 3 detections before creating a new track
                         (prevents phantom tracks from noise)
  - max_iou_distance = 0.7   → Max overlap distance for matching
  - max_cosine_distance = 0.4 → Max appearance distance for matching

FILES USED: backend/tracking.py

3.4  FastAPI  (Backend REST API)
══════════════════════════════════════

WHAT IT IS:
  FastAPI is a modern, high-performance Python web framework for building
  APIs. It is one of the fastest Python frameworks available (as fast as
  Node.js and Go).

WHAT IT DOES IN OUR PROJECT:
  Provides 20+ REST API endpoints that the frontend (and external systems)
  can call to interact with the CCTV system.

  Examples:
    GET  /api/cameras           → List all cameras
    POST /api/cameras           → Add a new camera
    GET  /api/unknown-persons   → Get all unknown faces
    POST /api/known-persons     → Register a new known person
    GET  /api/system/health     → Check if system is running

WHAT IS REST API?
  REST = Representational State Transfer
  It's a standard way for applications to talk to each other over HTTP.
  Like a menu at a restaurant — you place an order (request) and
  get food (response) without knowing how the kitchen works.

WHY WE CHOSE FASTAPI:
  - Automatically generates Swagger documentation (/docs)
  - Built-in data validation with Pydantic
  - Supports WebSocket for real-time communication
  - Async support for handling many requests simultaneously
  - 2-3x faster than Flask or Django for APIs

WEBSOCKET:
  Normal HTTP: Client asks → Server answers → Connection closes
  WebSocket:   Connection stays OPEN → Server pushes updates anytime

  We use WebSocket to stream live frame data and metrics to the
  dashboard without the browser constantly refreshing.

3.6  MySQL  (Database)
══════════════════════════════════════

WHAT IT IS:
  MySQL is the world's most popular open-source relational database.
  Data is stored in tables (like Excel sheets) with relationships
  between them.

OUR 7 DATABASE TABLES:

  1. cameras
     → Stores camera configurations (RTSP URL, location, FPS settings)
     → Columns: camera_id, name, location, rtsp_url, enabled, fps...

  2. known_faces
     → Registered persons (employees, staff, family members)
     → Columns: id, name, employee_id, department, face_embedding...

  3. known_face_images
     → Multiple photos per known person (for better accuracy)
     → Linked to known_faces via person_id (Foreign Key)

  4. unknown_faces  ← MOST IMPORTANT TABLE
     → Every unique unknown person detected
     → Columns: track_id, best_image_path, first_seen, last_seen,
                appearance_count, camera_id, confidence...
     → UNIQUE constraint on (track_id, camera_id) prevents duplicates

  5. unknown_face_images
     → All photos of each unknown person across sightings
     → Linked to unknown_faces via unknown_id

  6. detections
     → Every single detection event (known AND unknown)
     → Columns: camera_id, track_id, person_name, confidence, bbox,
                detected_at...
     → Used for timeline/history queries

  7. system_logs
     → Audit trail of everything that happens
     → Columns: event_type, description, severity, camera_id...
     → Severity levels: info, warning, error

CONNECTION POOLING:
  Instead of opening a new database connection for every query
  (which is slow), we maintain a POOL of 10 ready connections.
  Queries borrow a connection, use it, and return it to the pool.
  This is much faster for high-throughput systems.

FILES USED: backend/database.py + sql/init_db.sql

3.8  JWT Authentication
══════════════════════════════════════

WHAT IT IS:
  JWT = JSON Web Token
  It's a secure way to verify that an API request is from an
  authorized user without storing sessions on the server.

HOW IT WORKS:
  1. User logs in with username + password
  2. Server creates a token: "eyJhbGc..." (encoded string)
  3. User includes this token in every future request
  4. Server decodes the token to verify the user is legitimate
  5. Token expires after 60 minutes (configurable)

LIKE A CONCERT WRISTBAND:
  → You show ID once at entry (login)
  → You get a wristband (token)
  → Guards check your wristband (not your ID) every time you enter a zone
  → Wristband expires at midnight (token expiry)

WHY IT'S IMPORTANT:
  Without auth, anyone who knows your API URL could add/delete cameras,
  steal face data, or shut down the system.

FILES USED: backend/api/fastapi_server.py

══════════════════════════════════════
3.10  Python Threading
══════════════════════════════════════

WHAT IT IS:
  Threading allows multiple pieces of code to run SIMULTANEOUSLY
  in the same Python program.

WHY WE NEED IT:
  If we had only ONE camera, we could process it sequentially.
  But with 10 cameras, sequential processing means:
    Camera 1 takes 100ms → then Camera 2 takes 100ms → ... → 1 second total

  With threading:
    All 10 cameras process at the SAME TIME → still 100ms total!

HOW WE USE IT:
  Each camera gets its own dedicated thread:
    Thread 1: Reads Camera 1 frames continuously
    Thread 2: Reads Camera 2 frames continuously
    ...
    Thread 10: Reads Camera 10 frames continuously

  ThreadPoolExecutor manages up to 50 camera threads automatically.

THREAD SAFETY:
  When multiple threads access the same data (like frame results),
  we use a Lock (threading.Lock) to prevent conflicts:
    → Only one thread can write frame results at a time
    → Other threads wait their turn
    → No data corruption

SECTION 5: DATA FLOW FOR UNKNOWN PERSON DETECTION
------------------------------------------------------------------------

  STEP 1: Camera captures video frame
  STEP 2: YOLOv8 finds a face at position [100, 50, 150, 180]
  STEP 3: DeepSORT checks — "Is this face in any existing track?"
            → No match found → Create Track ID #7 (new person!)
  STEP 4: InsightFace generates embedding: [0.23, -0.45, 0.87, ...]
  STEP 5: Compare with all known faces in memory cache
            → Best match similarity = 0.42 (below 0.75 threshold)
            → Decision: UNKNOWN PERSON
  STEP 6: Check database: "Is Track #7 already saved for this camera?"
            → No → This is a NEW unknown person
  STEP 7: Save face image to disk: data/unknown_faces/unknown_cam1_20240505.jpg
  STEP 8: Create database record:
            track_id = "7"
            first_seen = 2024-05-05 14:23:11
            last_seen = 2024-05-05 14:23:11
            appearance_count = 1
            camera_id = "entrance_01"
  STEP 9: Mark Track #7 as "logged" (in memory)
  STEP 10: Send WebSocket alert to dashboard → "New unknown person!"

  --- 5 SECONDS LATER, SAME PERSON STILL IN VIEW ---

  STEP 1: Same face detected again
  STEP 2: DeepSORT recognizes → Track ID #7 (same person!)
  STEP 3: Check: "Is Track #7 already logged?" → YES!
  STEP 4: Just UPDATE the database record:
            last_seen = 2024-05-05 14:23:16
            appearance_count = 2
  STEP 5: NO new record created — zero duplicates!


------------------------------------------------------------------------
SECTION 6: DEDUPLICATION STRATEGY (WHY NO DUPLICATES)
------------------------------------------------------------------------

THREE LAYERS OF DEDUPLICATION:

  LAYER 1 — Track ID Memory (In-Memory, Per Session)
    → When a track is logged, we mark it in a Python set
    → Any subsequent frame with same track ID is skipped
    → Fast: O(1) lookup, microseconds
    → Limitation: Resets when system restarts

  LAYER 2 — Database Check (Persistent)
    → Before saving, query: SELECT * WHERE track_id=? AND camera_id=?
    → If found → UPDATE instead of INSERT
    → Persistent across system restarts
    → UNIQUE constraint in MySQL enforces this at DB level too

  LAYER 3 — UNIQUE Database Constraint
    → UNIQUE KEY (track_id, camera_id) in MySQL
    → Even if code has a bug, database physically prevents duplicate rows
    → Last line of defense

SECTION 8: HOW TO EXPLAIN THIS PROJECT IN AN INTERVIEW
------------------------------------------------------------------------

SHORT EXPLANATION (30 seconds):
  "I built a real-time AI surveillance system that connects to multiple
   IP cameras simultaneously. It uses YOLOv8 to detect faces, InsightFace
   to recognize whether they are known or unknown persons, and DeepSORT
   to track them across frames preventing duplicate database entries.
   Everything is exposed via a FastAPI REST API with WebSocket support
   for real-time updates, and visualized through a Streamlit dashboard."

MEDIUM EXPLANATION (2 minutes):
  "The system has three main AI components working in a pipeline:
   First, YOLOv8 detects all faces in each camera frame and gives us
   bounding box coordinates. Then DeepSORT assigns a consistent Track ID
   to each person across multiple frames — this is crucial because without
   tracking, the same person would create thousands of duplicate records
   per day. Finally, InsightFace converts each face to a 512-dimensional
   mathematical embedding and compares it against our registered persons
   database using cosine similarity. If the similarity is above 0.75,
   it's a known person; below 0.75, we save them as unknown.

   The backend is a FastAPI server with 20+ REST endpoints, JWT auth,
   rate limiting, and WebSocket connections for real-time streaming.
   MySQL stores all the data in 7 related tables. The frontend is a
   6-page Streamlit dashboard showing live metrics, an unknown persons
   gallery with filter/sort/identify actions, analytics charts, and
   a configuration panel for managing cameras and registered persons."

KEY CHALLENGES TO MENTION:
  1. Duplicate prevention — solved with 3-layer deduplication
     (in-memory set + DB check + UNIQUE constraint)
  2. Multi-camera scalability — solved with ThreadPoolExecutor
     (each camera runs in its own thread)
  3. Real-time performance — solved with:
     - Frame resolution downsampling (1080p → 480p for processing)
     - In-memory embedding cache (avoid DB query every frame)
     - Frame skipping (process every Nth frame based on FPS target)
  4. Camera disconnections — solved with exponential backoff
     reconnection strategy (wait 1s, 2s, 4s, 8s... up to 30s)
